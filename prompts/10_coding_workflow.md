# 10. 코드 구현·테스트 워크플로

## 계획 먼저

```text
요청 기능: {기능}
입력: {입력 데이터/형식}
처리: {핵심 로직}
출력: {파일/화면/지표}
완료 기준: {검증 가능한 기준}
제약: {언어/프레임워크/환경}

기존 파일 구조와 지침을 확인한 후 변경 계획과 영향을 받을 파일을 먼저 제시해줘.
과제 필수 범위 밖 기능과 과한 추상화는 만들지 마.
```

## 최소 기능 구현

```text
승인된 계획의 최소 기능만 구현해줘.
입력 → 처리 → 출력이 end-to-end로 동작하는지 먼저 확인해줘.
기존 동작을 깨뜨리지 말고, 변경 파일과 실행·검증 방법을 요약해줘.
```

## 기능 추가

```text
계획의 {단계 번호} 기능인 {기능명}을 추가해줘.
관련 파일은 {파일 목록}이고 완료 기준은 {기준}이야.
한 번에 이 기능만 변경하고, 기존 동작 및 예외 케이스를 확인해줘.
```

## 테스트

```text
{함수/기능}의 테스트를 작성하고 실행해줘.
정상 케이스와 빈 입력, 결측치, 잘못된 형식, 경계값 케이스를 포함해.
테스트가 실패하면 테스트를 임의로 약화시키지 말고 원인을 먼저 보고해줘.
```

## 코드 리뷰

```text
코드는 수정하지 말고 현재 구현을 요구사항과 수용 기준에 비추어 리뷰해줘.
1. 충족 / 부분 충족 / 미충족 항목
2. 계산·데이터 처리 버그 가능성
3. 처리하지 않은 예외 케이스
4. 보안·성능·재현성 위험
5. 남은 작업의 우선순위
```

## 실행 환경 유의

- 제공 환경에서 이미 정해진 실행 방식과 프레임워크를 우선합니다.
- 서버가 필요하면 제공된 환경의 공식 안내와 허용된 접속 방식에 따릅니다. 특정 바인딩 주소나 미리보기 기능을 가정하지 않습니다.
- 이미 설치된 패키지를 우선 사용하고 필요한 경우에만 최소한의 의존성을 설치합니다. 대회 환경에서 허용된 정상적인 설치 절차를 불필요하게 재확인하며 멈추지 말고, 승인 팝업이나 차단이 나타나면 화면 안내를 따릅니다.
- 공개 GitHub 레포 Clone/다운로드 등 안내서에서 허용한 가져오기는 허용된 경로로 진행합니다. 과제 데이터·파일·결과물을 외부로 전송하거나 외부 API에 보내지 않습니다. 차단된 네트워크 동작은 우회하지 않습니다.
- 테스트 실행과 미리보기는 작업 환경의 허용 절차를 따릅니다.
